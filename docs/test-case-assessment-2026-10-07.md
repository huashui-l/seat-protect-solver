# 座位保护测试体系评估与改造建议

评估日期：2026-10-07。状态：现状审计与设计建议；新基准尚未生成。

核对版本：`main@33f94a7`、当前 `cg-gurobi-direct@8b193c4` 及已暂存的迁入数据。40 个航班级输入和本次统计使用的 6 个座位图，其 JSON 内容均与 main 一致。生成器与通用验证规格在这两个提交间也一致。本次没有重新跑算法性能实验。

**结论：现有测试有保留价值，适合作为业务规则检查、开发和历史回归的基础；不足以独立支持“覆盖现实标准场景、证明某种算法普遍更优、问题已经充分解决”的结论。建议保留原案例，重建正式评测的分层、取样和验收方式，补充新版本数据。**

## 1. 标尺需要回答的三个问题

1. **正确性：**规则是否合法实现，固定座位、保护空座、陪护和跨组冲突是否被独立检查？有解、无解、超时未找到解能否区分？
2. **业务覆盖：**在约定的机型、人数、PNR 构成、资源压力和特殊需求范围内，能否持续给出可执行方案？
3. **算法效果：**相同输入、目标、硬件、核数、时间预算下，哪种方法更稳定、质量更好、取得可行解更快？与可证明最优值还有多远？

这三项不能只用一个平均 gap 代替。基准应能暴露方法的弱点，选择案例时不依赖哪种方法胜出。

本次以当前模型的“单航班换机、单一目标航班、组内同舱位、固定目标座位不可动、旅客与保护空座共同占用资源”为范围。SSR、陪护和隔离规则是**项目配置定义**，应由业务方确认，不能自动视为行业通行规则。超售后的旅客选择、跨航班分流、升降舱、拆分 PNR 属于额外业务决策，需先定义目标与允许行为；在当前全员分配合同下，可以先作为无解或不支持场景检测。

## 3. 缺陷及其影响

### 3.1 规模维度尚未分开控制

需要至少区分 `N`（旅客数）、`G`（PNR 数）、`Kmax`（最大 PNR）、完整组大小分布、目标容量和 `Q`。相同 N 下，75 个二人组和 15 个十人组对主问题、定价和局部搜索的压力完全不同。

现有 40 例虽然总体出现了 1–10 人组，但 10 人 PNR 只出现在 12 例中；CG30 中为 7 例。全部 40 例累计 1,496 个组，其中 8/9/10 人组分别只有 17/26/14 个。这只是覆盖统计，正反方向相关案例不能当成独立抽样。

建议在固定 N、Q、机型及特殊规则量的条件下，分别控制小组为主、家庭组为主、大组较多。单 PNR 5–10 人脚本保留作诊断，但补充多 PNR 竞争；超过 10 人是否需要 15/20 人压力档，要以业务允许的 PNR 上限为准，不能为了方便求解擅自拆组。

### 3.2 full 与目标满载混淆，宽体规模不足

`reverse:full` 的 Q=184，是共同可转移容量满载；面对 336 座目标飞机，实际资源负载只有 54.8%。商务舱为 16/36=44.4%，经济舱为 168/300=56%。它是有价值的扩容对照，不能证明目标宽体满载时也能求好。

D4 所有转换的需求规模各固定一个值，均未达到目标资源负载 90%。新基准应补宽体→宽体的 200/250/300 人级案例、高负载支线/窄体、相同布局不同分舱/特殊座位配置，以及舱位不均衡压力。

对于小机型→大机型的合法单航班扩容，不能凭空要求目标 97% 满载：旧机型本身装不下。应同时记录相对于共同可转移容量的负载和相对于目标容量的负载；目标宽体高负载由宽体来源案例承担。

### 3.3 “难度”是多个因素混合的场景标签

normal→edge 同时改变 PNR 分布、SSR、固定比例、保护空座、隔离与旧座位分散程度。固定比例反而下降，可能增加搜索自由度，也可能减轻几何阻塞；不存在必然的难度单调关系。D4 各档还使用不同随机种子，因此不是在同一实例上只增强一个因素。

应保留旧标签用于追踪历史，但新表以实际因素为主。用成对的控制实验回答“增加大 PNR/提高固定比例/减少摇篮位后会怎样”。运行后可以追加实测求解难度，但不能用某一个算法的耗时定义整套中立基准的难度。

### 3.4 规则出现了，但关键组合没有系统覆盖

40 例全部包含七类 SSR。小 normal 例有 46 名旅客、7 名 SSR，占比 15.2%，与场景参数里的 7% 不同，原因包括每类至少出现一次的覆盖要求。这样的设计适合功能覆盖，不能直接解释为真实航班分布，也缺少正式航班级的无 SSR、稀疏 SSR 对照。

生成器在 Q 达到共同可转移容量时关闭 `sameRowNoOtherSSR` 和 `sameSubRowNoOtherSSR`；实查 6 个 Formal24 full 案例这两项均为 0。固定座位生成还排除了带单/双侧保护规则的旅客，40 例此类“自身固定且要求空座”的人数均为 0。小例/单元测试有部分覆盖，但大规模压力并未覆盖。

优先补：高负载＋隔离、固定受保护旅客、部分组员固定＋陪护、摇篮/过道等特定资源恰好耗尽、同舱资源不足但整机有空座、多个组争用同一保护资源、可用座位碎片化。组合无法合法实现时，应记录不可行原因，不能偷偷降低规则后继续沿用原标签。

### 3.5 生成器偏向它能构造出来的可行实例

当前生成器会重采样特殊角色，使用有界候选和 DFS 找旧/新机型的特殊资源见证，必要时归一化部分隔离规则。这有助于生成合法数据，但意味着样本是“通过当前构造过程筛选”的条件分布。

建议明确分开：可行构造集、稀缺资源压力集、可证明不可行集、真实回放集。对可行集保存**最终输入（含所有固定座位）下的完整可行见证**，独立验证，评测时不提供给算法。特殊组的中间 witness、单组均可放置或容量检查通过，都不能替代最终完整见证。生成失败须记录原因，不可把搜索超时等同于数学无解。

### 3.6 CG30 的选样与调参历史限制了外推

provenance 明确记录：另 10 个 D4 没有可用 CG 整数参考与许可证限制有关。CG30 因而是“已有参考结果的 30 例”，不是按业务覆盖均衡选择的 30 例。不能因参考算法跑不了就把案例从新正式分母里移除；可行性和耗时照常评，参考 gap 标记缺失。

同一 provenance 记录检查过 70 次有效全语料运行，并根据 CG30 表现筛选方案。CG30 已参与开发选择，适合作开发/回归集。它能证明在这些已知输入上的改进，不能独立证明未见场景上的优势。新正式集需要未参与调参的种子，并增加未参与开发的座位图/场景组合；一次冻结后，失败也必须报告。

### 3.7 参考分数与时间口径不能直接解释成算法排名

CG30 的 30 个参考均标为 `gap_CG_integer`，预算混合 150/600 秒，是历史列池整数可行分数，不是全局最优证书。历史启发式相对某参考出现约 -8.95% 的差值，表示找到了更好的可行解，不能叫“超过最优解”。其他正 gap 也不能被称为距最优差距。

历史 provenance 还说明部分 D4 运行与回归测试重叠，耗时属于观察结果。已有 main 的 5 秒结果和长时 CG 结果可以作为“短时方案对离线参考”的比较，不能据此作同预算、公平核数下的速度排名。

### 3.8 文档与验收存在漂移

通用规格实际为 13 例（11 合法＋2 非法），旧说明写成 12。现已为 11 个合法例补齐完整可行参考分配、参考分数和参考状态，并由独立评分器复核。`full_resource_protection_heavy` 的 `expectedCurrentHeuristicComplete=false` 使普通完成性测试跳过当前启发式求解；保留它作为已知缺陷回归很有价值，但不能算作算法完成测试通过。本次没有复跑该案例的最新算法性能。

Formal24 旧 manifest 的 24 个输入哈希匹配 CRLF 字节，而当前文件与 CG30 清单匹配 LF 字节，JSON 语义未变。本次明确识别了换行差异。新版本应固定序列化方式、同时保存原文件哈希及语义规范化哈希，不能静默改写历史工件。

当前分支迁入了 main 的部分 native 测试，但没有迁入完整配套实现和 D4 生成脚本。跨分支“有测试文件”不等于这些测试均可运行。正式验收应在各自可构建的实现版本上执行，统一输入与外部评估器。

| 13 个通用小例 | 全部保留并补齐显式见证/非法原因 | 包括重压失败例和扩容负对照；修复缺陷后提升完成性要求 |

| CG30 清单和历史结果 | 原样存档，作为上述数据的命名视图 | 不重复计成新的 30 个样本；旧参考不得冒充最优值 |
| 单 PNR 5–10 人脚本 | 保留并扩充多 PNR 竞争诊断 | 分离定价增长与整机协调的耗时来源 |

## 5. 新测试体系的建议规格

### 5.1 规则与证书层：小而可解释

在已有 13 例基础上，优先增加 8 组可行/不可行配对规格（16 例）：舱位容量、摇篮位、过道及出口限制、陪护邻接、固定保护空座、跨组保护共享、条件隔离、碎片化联合放置。尽量仅改变一个资源或固定要求，使预期原因可审查。

“输入字段/组结构非法”“合法结构但约束无解”“已知可行但求解超时”分别标注。另给实际支持的算法设置极短截止时间，检验其不会把未知状态错误报告为无解或最优。

保留现有 CG 穷举对照，建立共享的小规模最优基准，初期约 24 例；以独立穷举确实可完成的规模为准，例如 4–10 名旅客、少量有效座位、2–5 个 PNR。逐步覆盖保护空座、陪护、固定、跨组隔离和完整软分，而不仅检查普通分配。

### 5.2 主覆盖层：先制定 72 个规格，再做多种子

一个可执行的首版结构是 **8 类转换 × 3 档共同可转移资源负载 × 3 类 PNR 构成 = 72 个规格**。每规格先 3 个独立生成种子，共 216 例；正式统计建议至少 5 个，共 360 例。它是覆盖设计起点，不是已经有现实频率依据的抽样比例。

| 维度 | 建议取值 | 约束 |
|---|---|---|
| 8 类转换 | 2-2→2-3、反向；3-4-3→3-3、反向；3-4-3→3-3-3、反向；3-4-3→2-4-2；3-3→另一份 3-3 配置 | 后一类须改变舱位/特殊座位布置；无变化同机型另作负对照 |
| 资源压力 | 共同可转移容量约 60%/85%/97% | 同时报告目标整机及分舱 N/C、Q/C；考虑整数取整和特殊资源可行性 |
| PNR 构成 | 1–2 人为主；3–6 人家庭组为主；7–10 人组占比较高 | 记录完整直方图；同规格内尽可能固定 N、Q 等其他因素 |
| 特殊需求 | 固定一套明示的基础分布 | 不强制每例含全部 SSR；无真实比例时标“合成假设” |
| 随机性 | 各规格多个生成种子 | 生成种子和算法随机种子分开管理 |

大机型两侧都有容量时，应检查生成结果真正进入 200/250/300 人档；只有大座位图却仍只有 150 人不算覆盖。若 97% 档由于稀缺资源确实无解，应留下该设计点及原因，并进入边界层，不能反复降低约束后当成原档的成功样本。

先用旧 40 例和开发专用新增数据改实现、调参。正式种子与部分拓扑/交互组合保留到算法及评测协议冻结后再运行；每个正式输入对所有方法完全相同。若看了正式结果再改算法，该轮已成为开发资料，应另留新的最终验证集。

### 5.3 因素诊断层：补主基准无法解释的原因

不建议将每个维度全部笛卡尔相乘。固定一组基础输入，逐项扫描下列因素，并预先列出重点两两交互；例如高负载×大 PNR、高固定比例×陪护、高负载×保护空座、舱位瓶颈×摇篮位。对无法保持其他因素不变的配对，在元数据中说明。

| 因素 | 建议覆盖 |
|---|---|
| N | 小例；约 50/100/150/200/250/300，机型允许范围内 |
| G、Kmax 与分布 | 同人数多小组/少大组；至少分别触及 1/2/4/6/8/10 人组上限 |
| 固定旅客比例 | 0/10/30/60%；部分组员固定、全部固定对照；固定位置集中与分散 |
| SSR | 无 SSR、稀疏、较多；每类单独出现、典型组合、资源竞争 |
| 保护空座 | 无保护、单侧为主、双侧、混合；记录实际保护座位数而非仅旅客数 |
| 资源紧张程度 | 90/95/98/100% 可行边界；总量有余但特定舱位/属性不足 |
| 旧座位及偏好 | 原本紧凑/已分散；可原样保持/属性损失不可避免；窗口过道、同行紧凑度之间的权衡 |
| 拓扑 | 不同排数/过道/舱位边界；真实机型变体；移除不可用座位的模型能力需先确认 |

原始分值、每旅客损失、同行跨排/分散、属性保留和固定座位违规等均应能解释到业务层。业务未要求“所有人相邻”时，不能把 PNR 分散一概当硬违规；用对应软指标衡量。

### 5.4 真实回放层

取得经授权、去标识化的航班配置和 PNR/特殊需求分布后，覆盖换小、换大、同容量换布局、特殊资源减少等事件。保护拓扑、组大小与约束关联，匿名化不能抹掉造成困难的结构。至少保留一部分日期/机型家族作为未参与开发的验证集。

在没有真实回放或业务确认前，可声称“通过约定合成场景”，不能声称“已充分代表现实航班”。覆盖集合等权重用于诊断能力；若要估计线上平均收益，应按实际场景发生率另做加权报告。

## 6. 比较列生成与混合启发式的统一协议

| 项目 | 建议协议 |
|---|---|
| 公平输入 | 同一规则、权重、固定座位、有效座位域和独立完整评分器；记录哈希 |
| 时间 | 同预算比较 5/30/60 秒；另做 300/600 秒离线参考，不混成速度排名 |
| 硬件 | 同机器；单核诊断与相同总核数的部署配置分别报告，固定各模型线程和外层并发 |
| 热启动 | 分别报告从零开始与共同初始解；共享初始解的获取成本单列并计入所声称的端到端预算 |
| 基线 | 简单合法贪心/修复、当前混合启发式、启发式定价 CG；小中例尽可能加完整直接模型；用模块消融解释收益 |
| 重复 | 每个输入、预算和方法先至少 5 次；使用预定算法种子、交错/随机运行顺序，报告每次结果，禁取各例最优后拼接 |
| 状态 | 完整合法、已知可行但未找到、已证无解、未知、运行失败、超时分别统计 |
| 主指标 | 预算内完整合法比例、首次完整合法解耗时、最终完整业务得分及分项、峰值内存、端到端耗时 |
| 质量基准 | 已证整数最优值、有效全空间上界、当前最好已知可行解分栏；缺失参考照常报告其他指标 |
| 算法诊断 | LP/定价轮数、生成列数、定价耗时、整数主问题耗时、回退次数；这些辅助解释，不代替业务结果 |
| 汇总 | 分机型/负载/PNR/规则组合统计；配对胜平负、分位数及置信区间；按输入/场景家族聚合，不能把同实例多次运行当独立航班 |

质量仅在完整合法解之间比较，同时保留全部输入的失败率，防止只选两种方法均成功的容易案例而掩盖失败。若综合排序，先按可行性和业务服务要求分层，再比较质量，不能让非法高分获胜。

对最大化评分 S：有已证最优值 S* 时报告最优差距；只有已知可行参考 B 时，报告“相对已知可行参考差值”；有经验证的全空间上界 U 时，可报告 U−S 的剩余空间。受限列池的 LP 值不能未经完整定价/安全界认证直接充当 U。启发式定价没找到负列也不是最优证明。

历史有符号平均差值可能被少数大幅胜出的案例抵消。应同时报告胜平负、最差分位和正向落后程度；避免仅凭平均接近 0 声称每个场景都好。得分接近 0 时百分比尤其敏感，应同时给绝对差及每旅客差。

## 7. 改造顺序与完成标准

1. **整理现状：**修正文档计数与参考解描述；保留旧清单/哈希，输出覆盖明细。当前评估已完成此步的静态审计。
2. **补验收：**补小例完整见证、边界配对、状态检查和共享精确小例；重压例继续显式暴露，直到实际修复并通过。
3. **改生成器：**把旅客数、PNR 分布、固定比例、SSR 与资源压力拆开配置，输出请求参数和实际参数、重采样/放宽记录及最终完整见证。当前已落地新版 72 规格开发生成器和正式 5 种子计划；开发集不替代冻结 Formal24/D4。
4. **生成新版本：**建立开发/正式分离的 V2，先核对覆盖矩阵，再冻结 manifest。旧 Formal24/D4 不原地覆盖。
5. **统一跑分：**按同预算协议运行所有方法，质量不足和运行失败同样入表。形成时间—质量曲线与场景分项报告。
6. **业务验收：**由业务方确定允许 PNR 上限、机型与规则范围、端到端时限、成功率目标及可接受质量损失；再判断哪些范围已解决，哪些需回退或继续研发。

当前不能仅凭“30 例通过”判定充分解决。完成标准至少包括：业务规则覆盖可追踪；小例与独立真值一致；所有预先冻结场景均有结果；已知可行失败被单独报告；速度与质量在未参与调参的实例上达到预先约定的目标；真实回放验证通过或明确尚缺。
